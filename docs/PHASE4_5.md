# Phase 4.5 — Low-Permission Portfolio Supervisor Agent

Phase 4.5 adds an Agent-facing supervision layer over the deterministic Phase 4 portfolio engine. It does **not** create an LLM portfolio manager.

`PortfolioHealthSnapshot` is immutable evidence. It contains health checks, all portfolio-constructor benchmark summaries, stress results, target/current weight drifts and the deterministic rebalance result.

## Health policy

The monitor supports explicit deterministic thresholds for:

```text
max data age
max forecast age
minimum expected net return
maximum forecast volatility
maximum turnover
maximum stress loss
```

No threshold is generated by the Agent. Optional threshold values remain configuration owned by deterministic infrastructure.

The resulting severity is ordered:

```text
OK < WARNING < CRITICAL
```

Stale data/forecasts and excessive configured stress loss can create CRITICAL evidence. Soft portfolio diagnostics such as low expected net return, high volatility/turnover or an existing rebalance trigger create WARNING evidence.

## Finite Supervisor actions

Read actions:

```text
inspect_portfolio_health
inspect_portfolio_benchmarks
inspect_stress_report
inspect_rebalance_decision
list_operating_policies
```

Non-mutating requests:

```text
request_operating_policy
request_rebalance
request_human_review
```

The Supervisor does not have `set_portfolio_weights`, `bypass_risk_gate`, fill-selection or broker-order tools.

`request_operating_policy` and `request_rebalance` require human approval. Their handlers only validate and create a payload with:

```text
mutation_performed = false
```

## Reference Supervisor behavior

The deterministic reference runtime first reads the complete supervision evidence. It then applies:

```text
CRITICAL
 -> request pre-registered defensive policy
 -> request human review
 -> BLOCKED pending approval

WARNING + deterministic rebalance=True
 -> request rebalance
 -> BLOCKED pending approval

WARNING
 -> request human review
 -> BLOCKED

OK
 -> no request
 -> COMPLETED
```

This behavior is deliberately deterministic. An LLM may later produce explanations or recommend among already registered policies, but must remain behind the same ToolRegistry and approval boundary.

## Operating policy registry

The reference registry exposes:

```text
normal
cautious
defensive
paused
```

Each policy names deterministic constraint/rebalance policy identifiers. The Agent cannot create new numeric limits through this registry.

## Persistence

```text
SQLitePortfolioSupervisionStore
  -> immutable health snapshots

SQLiteAgentAuditStore
  -> every inspect/request/policy result
```

A snapshot id cannot be overwritten with different evidence.

## Scope boundary

Phase 4.5 does not implement:

```text
automatic approval of policy/rebalance requests
broker execution
live account mutation
kill switch implementation
corporate actions
reconciliation
state recovery
production alert transport
```

These are Phase 5 paper/shadow production concerns.

## Phase 5 handoff

Phase 5 should attach operational adapters to the already separated request/application boundary:

```text
Supervisor request
   -> human/operational approval
   -> deterministic operational controller
   -> paper broker
   -> reconciliation
   -> observed state
```

This preserves the rule that an Agent may supervise financial state without owning it.
